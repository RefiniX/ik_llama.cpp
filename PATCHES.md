# CPU performance patches for ik_llama.cpp

A set of CPU-side patches on top of ik_llama.cpp `8d50c6ff` (2026-11-18), written and benchmarked on a dual-socket Cascade Lake box. My own patches are offered as-is: anyone may take, rewrite or submit them, under their own name, with no attribution needed. Two patches are other people's work, included under the project's MIT license; please credit their authors if you reuse them: NUMA weight/KV mirroring on `numa-mirror-8d50c6ff` (written by mikechambers84, rebased by sultanqasim; my port adds the KV resyncs) and the qwen35 pre-tokenizer split (Kabir Potdar, ggml-org/llama.cpp#22110). I will not be maintaining these branches or turning these into PRs myself.

**AI disclosure:** the investigation, the patches and the benchmarks were done by an AI agent (Claude Code with Claude Opus and Claude Fable models) on my machine, under my direction. I have been running these builds in daily use; I have not independently re-derived the analysis. Please test on your own hardware before relying on any of it.

## Branches

- `cpu-perf-8d50c6ff`: 14 patches (one commit each), none of them NUMA-specific. Each one is useful without the others, except that the MXCSR one fixes the denormal one.
- `numa-mirror-8d50c6ff`: `cpu-perf-8d50c6ff` plus NUMA weight mirroring, expert row placement and four token-generation patches that rely on the mirror's thread pinning (nine commits). This is invasive and only matters on multi-socket machines; see #2396 for the upstream discussion.
- `cpu-perf-41d123e9`, `numa-mirror-41d123e9`: the previous snapshot, left unchanged.

These branches are a snapshot and will not be rebased. A newer base, if ever published, gets new branch names.

**~~Struck-through~~ rows** are patches that upstream already has, or for which a better approach is known (a different mechanism, or a much smaller way to get the same effect). They stay on the branch because this is what I run, but should not be taken as they are. Rows that are not struck but list fixes under "known issues" are fine in approach and need only the small fix described.

Output check for this snapshot (2026-11-18, Qwen3.6-35B-A3B fine-tune, five prompts, seed 201, no MTP, `--numa numactl`): `cpu-perf-8d50c6ff` gives the same output as plain `8d50c6ff` (5/5 md5), as my build on `41d123e9` did against plain `41d123e9` (5/5). Outputs differ from the `41d123e9` snapshot because upstream changes between the two bases changed them (plain `41d123e9` vs plain `8d50c6ff`: 0/5). `numa-mirror-8d50c6ff` was run with Qwen3.8 against my `41d123e9`-based build: coherent output at the same speed, different md5, which I attribute to the same base change (not checked against plain `8d50c6ff`).

Numbers are per patch (A/B with and without it, or an isolated benchmark of the changed function), measured between 2026-11-07 and 11-18 on slightly different bases, most with the NUMA mirror patch applied. Re-measure on your own hardware.

Test machine: 2x Xeon Gold 5220 (Cascade Lake, 18 cores, 2.2 GHz base / 3.9 GHz turbo, AVX-512 VNNI, no AVX512_BF16). Memory: 12x 16 GB DDR4-2666 dual-rank RDIMM, one per channel, all 6 channels of each socket populated (192 GB). The runs use an LXC container limited to 36 cores (18 per socket) and 128 GB, CPU only, `-t 32`, no SMT. Measured here: one core copies about 3.9 GB/s (memcpy of 60 MiB); 18 threads read 107 GB/s from their own node and 33 GB/s from the other one; generation reaches about 98 GB/s effective with NUMA mirroring and about 62 GB/s with `numactl --interleave=all`. Not tested on AMD, ARM, Windows, macOS or GPU builds.

How the numbers may transfer: this box has slow cores, low single-core bandwidth and two sockets, which makes some of these patches look bigger than they will on a desktop.

- Patches that remove a fixed amount of work per token or per MTP round (per-step state restore, repetition penalties, the vocab sort, the qwen35 tokenizer, the checkpoint copies) remove the same work everywhere, but that work costs less on fast cores. For example the 60 MiB state copy behind the restore patch takes 16-17 ms on one core here and about 3.5 ms on a Ryzen 7 PRO 5850U laptop core (17.5 GB/s).
- The few-row quantization, small-batch flash-attention and the two Qwen3.8 long-context patches were measured only with two sockets and 32 threads. Their effect on a single socket, and the best thresholds for the flash-attention one, are unknown. The Qwen3.8 ones remove single-threaded work whose cost does not depend on the core count, so they should help wherever the batch has fewer rows than threads.

| ~~`llama : multi-threaded per-step recurrent state restore on CPU`~~ | restoring SSM state after a rejected MTP draft used one thread (CPU has no async copy) | bit-identical | qwen35moe 35B-A3B fine-tune, IQ4_XS, KV q8_0: restore 18.3 -> 2.1 ms (~60 MiB of state) | **better approach:** do not copy at all. ## numa-mirror-8d50c6ff

| commit | what | measured here | known issues |
|---|---|---|---|
| ~~`numa : NUMA weight/KV mirroring (Mike Chambers' implementation)`~~ | one copy of the weights per node, threads pinned per node, two-level barrier for small batches. Original code by mikechambers84, rebased by sultanqasim; this port adds resyncs for KV writes that bypass the graph | Qwen3.6-35B-A3B Q6_K-class fine-tunes: generation +30-60% vs `numactl --interleave` | use `--numa mirror --numa-mirror weights`. **Better approach:** drop KV mirroring (the default `all` is 4-21% slower, and the mirrored SSM state is never read); a weights-only version that swaps `src0` at the matmul entry points and finds the copies through an address range table (no `ggml_tensor` field) would be roughly 250 lines instead of ~1000 |
| `numa : add --numa-mirror dense for models that do not fit twice` | mirror only the tensors every token reads in full (attention/SSM, router, shared experts, output) | +2.7-2.9 GiB; Qwen3.8-Flash-Next IQ4_XS x1.17, gpt-oss-120b x1.23 (vs interleave) | selects tensors by name; selecting by graph use (src0 of `MUL_MAT` but not of `MUL_MAT_ID` / `GET_ROWS`) would be robust and cover tied outputs; one 2 MiB-rounded allocation per tensor; does not force `--no-mmap` |
| ~~`numa : mirror the output projection of tied-embedding models with --numa-mirror dense`~~ | dense skipped every tensor named `token_embd`; a model without `output.weight` (Gemma) projects the logits with it, read in full every token | Gemma 4 26B-A4B QAT, no MTP: dense 33.6 -> 35.0 t/s | not needed once dense selects tensors by graph use |
| `numa : place routed expert rows on the node whose threads compute them (experimental)` | keeps one copy of the routed experts but places each expert's row ranges on the node of the threads that compute them | with `dense`: Qwen3.8 x1.32, gpt-oss-120b x1.46 (vs interleave; dense alone x1.17 / x1.23); no extra memory; output unchanged | experimental: `MPOL_BIND` (a full node fails instead of falling back), new mappings are never unmapped, assumes `-t == -tb`; verified on 2 nodes only |
| `numa : select expert row placement with --numa-mirror rows / shard instead of an env var` | `--numa-mirror rows`, or `shard` = `dense,rows` | Qwen3.8 server, dense -> shard: 17.6 -> 19.8 t/s | the option should become its own flag (placement is independent of mirroring) |
| ~~`ggml : dissemination barrier for the NUMA-pinned token generation path`~~ | log2(nth) rounds, each thread writes only its own flag: 2.8 -> 1.1 us per barrier (Qwen3.8 runs about 2800 per token); `GGML_NUMA_BARRIER=hier` restores the two-level barrier | Qwen3.8 token generation x1.07 | **does not build on Windows** (`atomic_llong` and `*_explicit` are not shimmed); global state, spins without yielding, only active with the mirror. **Better approach:** a general barrier with per-graph state, a yield after N spins and Win32 atomics, used for every decode graph |
| ~~`ggml : fuse small token-generation nodes (tiny mat-mul after mat-mul, SCALE+SILU, MULTI_ADD+SCALE)`~~ | idle threads compute small matrices that share the previous op's input; two element-wise fusions | bit-identical; x1.03 together, but SCALE+SILU alone is within noise and MULTI_ADD+SCALE alone was slower | **better approach:** drop the element-wise fusions; for the tiny mat-mul, let the existing consecutive-`MUL_MAT` loop accept a second quantization type. Thread-local buffer leaks without OpenMP |
| ~~`ggml : quantize a large few-row src1 on the first 4 threads`~~ | large few-row inputs (Qwen3.8 `mix_down` in MTP verification) quantized by 4 threads instead of 1 | bit-identical; B=6 -4.5% time | constants (4 threads, 40000 values) tuned on this machine; belongs with the one-line form of the few-row quantization commit |
| `iqk : split the fused MoE up/gate evenly, rotate it per expert, masked SiLU tail` | the ceil split left threads idle (27 of 32 working); even split, rotation of who gets the extra unit, AVX-512 masked SiLU tail so the split does not change values | B=1 -3.9%, B=6 -4.9% time; Qwen3.8 output differs in the last bits from the previous version (top token unchanged), other models bit-identical | the rotation calls mirror functions and one hunk edits the expert-row placement; for use without the mirror, rotate by `(ith + expert index) % nth` |

Together the four token-generation commits measured in the server: Qwen3.8 x1.14 (no MTP) / x1.16 (MTP), Qwen3.6 x1.08 / x1.04, Occamy x1.07 / x1.02, Gemma 4 x1.13 / x1.09, gpt-oss-120b x1.03.
